# API Health Monitor

Backend-сервис на Go для мониторинга доступности HTTP-эндпоинтов. Позволяет управлять списком отслеживаемых URL, автоматически выполнять проверки доступности, сохранять историю результатов и получать информацию о состоянии проверяемых эндпоинтов.

## Функции

- CRUD для отслеживаемых HTTP-эндпоинтов.
- Настраиваемый интервал автоматических проверок.
- Ручной запуск проверки эндпоинта.
- История результатов проверок.
- Измерение времени HTTP-ответа.
- Обработка сетевых ошибок и таймаутов.
- SSRF-защита с проверкой DNS-разрешения.
- Параллельное выполнение проверок через worker pool.
- Защита от одновременной проверки одного эндпоинта с помощью DB-backed locks.
- Graceful shutdown HTTP-сервера и Scheduler.
- Структурированное логирование.

## Технологии

- **Go** — основной язык разработки.
- **net/http** — HTTP-сервер и клиент.

- **Docker Compose** — локальное окружение.
- **golang-migrate** — управление SQL-миграциями.
- **log/slog** — структурированное логирование.

### Основные компоненты

- **Transport** — HTTP-обработчики, DTO, валидация входных данных и формирование JSON-ответов.
- **Repository** — взаимодействие с PostgreSQL через `pgxpool`.
- **Checker** — выполнение HTTP-запросов к отслеживаемым эндпоинтам, обработка таймаутов и сетевых ошибок, измерение времени ответа и защита от SSRF.
- **Service** — координация процесса проверки: получение эндпоинта, запуск Checker и сохранение результата.
- **Scheduler** — периодический запуск проверок активных эндпоинтов с ограничением параллелизма.
- **Server** — регистрация HTTP-маршрутов.
- **Config** — загрузка конфигурации из переменных окружения.
- **Main** — инициализация зависимостей, запуск HTTP-сервера и Scheduler, graceful shutdown.

### Планировщик

Планировщик(scheduler) автоматически находит эндпоинты, которые необходимо проверить.

Основные характеристики:

- Интервал опроса Scheduler — 5 секунд.
- Максимальное количество одновременно выполняемых проверок — 5.
- Проверяются только активные эндпоинты.
- Следующая проверка определяется на основе времени завершения предыдущей проверки и настроенного интервала.
- Для предотвращения одновременной проверки одного эндпоинта используется DB-backed locking.
- Ошибка проверки одного эндпоинта не останавливает обработку остальных.
- При отмене контекста Scheduler прекращает работу.

## HTTP API

Базовый путь: `/endpoints`.

### Управление эндпоинтами

| Метод | Путь | Описание | Статус |
|---|---|---|---|
| POST | `/endpoints` | Создать эндпоинт | 201 |
| GET | `/endpoints` | Получить список эндпоинтов | 200 |
| GET | `/endpoints/{id}` | Получить эндпоинт по ID | 200 |
| PATCH | `/endpoints/{id}` | Обновить параметры эндпоинта | 200 |
| DELETE | `/endpoints/{id}` | Удалить эндпоинт | 204 |

Дополнительные возможности:

- Фильтрация списка по `is_active`.
- Настройка интервала проверки при создании и обновлении.
- Изменение активности эндпоинта.
- URL нельзя изменить после создания.

### Проверки

| Метод | Путь | Описание | Статус |
|---|---|---|---|
| POST | `/endpoints/{id}/checks` | Запустить проверку вручную | 200 |
| GET | `/endpoints/{id}/checks` | Получить историю проверок | 200 |

История проверок:

- Сортируется от новых результатов к старым.
- По умолчанию возвращается до 20 записей.
- Максимальный размер выборки — 100 записей.
- Размер выборки задаётся параметром `limit`.

Пример:

```http
GET /endpoints/1/checks?limit=5
```

Для несуществующего эндпоинта возвращается `404 Not Found`.

## Checker and Security

Checker отвечает за выполнение HTTP-проверок.

Особенности реализации:

- Поддерживаются HTTP и HTTPS.
- Используется настраиваемый timeout (10 секунд в текущей конфигурации приложения).
- Измеряется время до получения HTTP-заголовков.
- Обрабатываются сетевые ошибки и таймауты.
- HTTP-редиректы не выполняются автоматически.
- Для освобождения ресурсов закрывается response body.

### SSRF Защита

Для защиты от Server-Side Request Forgery реализован собственный Safe Dialer.

Перед установлением соединения:

1. Проверяется URL и допустимость схемы.
2. Выполняется DNS-разрешение hostname.
3. Проверяются все полученные IP-адреса.
4. Запрещается соединение с непубличными IP-адресами.
5. Соединение устанавливается непосредственно с проверенным IP.

Это предотвращает обращение к внутренним сетям и локальным сервисам через отслеживаемые URL.

## База данных

Используются две таблицы.

### monitored_endpoints

Хранит информацию об отслеживаемых эндпоинтах:

- уникальный URL;
- интервал проверки в секундах;
- признак активности;
- время создания и последнего обновления.

### check_results

Предназначена для хранения истории проверок:

- ссылка на отслеживаемый эндпоинт;
- HTTP-статус;
- время ответа;
- время начала и завершения проверки;
- сообщение об ошибке;
- вычисляемый признак успешности.

Поле `is_success` вычисляется PostgreSQL на основе HTTP-статуса `2xx`. При удалении эндпоинта связанные результаты удаляются каскадно.

Время ответа измеряется до получения HTTP-заголовков, а не до полной загрузки тела ответа.

## Тестирование

В проекте используются:

- **Transport Tests** — проверка HTTP-обработчиков, валидации и JSON-ответов с помощью `httptest`.
- **Checker Unit Tests** — проверка HTTP-ответов, сетевых ошибок, таймаутов, отмены контекста и SSRF-защиты.
- **Repository Integration Tests** — проверка взаимодействия с PostgreSQL.
- **Service Unit Tests** — проверка бизнес-логики с использованием fake-зависимостей.
- **Scheduler Unit Tests** — проверка периодических задач, ограничения параллелизма, обработки ошибок и отмены контекста.

Запуск всех тестов:

```bash
go test ./... -v
```

Для интеграционных тестов репозитория требуется отдельная тестовая база данных, указанная в `TEST_DATABASE_URL`. На ней должны быть применены SQL-миграции.

Полезные команды:

```bash
gofmt -w ./cmd ./internal
go vet ./...
go test ./...
go test -race ./...
golangci-lint run
```
