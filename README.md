# API Health Monitor

[![CI](https://github.com/bidmybl/api-health-monitor/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/bidmybl/api-health-monitor/actions/workflows/ci.yml)

**API Health Monitor** — backend-сервис на Go для мониторинга доступности HTTP-эндпоинтов. Позволяет управлять отслеживаемыми URL, запускать проверки вручную и автоматически, сохранять историю результатов и получать информацию о состоянии эндпоинтов.

Проект демонстрирует практическую работу с Go, HTTP API, PostgreSQL, конкурентным программированием, тестированием, Docker и CI.

## Возможности

- CRUD для отслеживаемых HTTP-эндпоинтов.
- Настраиваемый интервал автоматических проверок.
- Ручной запуск проверки эндпоинта.
- История результатов проверок.
- Измерение времени до получения HTTP-заголовков.
- Обработка сетевых ошибок и таймаутов.
- SSRF-защита с проверкой DNS-разрешения и IP-адресов назначения.
- Параллельное выполнение проверок через worker pool с ограничением конкурентности.
- Защита от одновременной проверки одного эндпоинта с помощью PostgreSQL advisory locks.
- Graceful shutdown HTTP-сервера и Scheduler.
- Структурированное логирование.

## Технологический стек

- **Go 1.27.3**
- **net/http** — HTTP-сервер и клиент.
- **PostgreSQL 18** — хранение данных.
- **pgx/v5, pgxpool** — драйвер PostgreSQL и пул соединений.
- **golang-migrate** — SQL-миграции.
- **Docker, Docker Compose** — контейнеризация и локальное окружение.
- **log/slog** — структурированное логирование.
- **testing, httptest** — тестирование.
- **GitHub Actions** — CI.

## Быстрый запуск

### 1. Подготовить переменные окружения

Скопировать пример конфигурации:

~~~bash
cp .env.example .env
~~~

Заполнить `.env`:

~~~dotenv
POSTGRES_PASSWORD=your_local_password
DATABASE_URL=postgres://health_monitor:your_local_password@db:5432/health_monitor?sslmode=disable
TEST_DATABASE_URL=
~~~

`DATABASE_URL` используется контейнерами приложения и миграций. Поэтому hostname здесь — `db`, имя сервиса PostgreSQL в Docker Compose.


### 2. Запустить приложение

~~~bash
docker compose up --build -d
~~~

Docker Compose:
1. Запускает PostgreSQL.
2. Дожидается готовности базы через healthcheck.
3. Применяет SQL-миграции.
4. Собирает и запускает API.

Сервер доступен на `http://localhost:8090`.

Остановить окружение:

~~~bash
docker compose down
~~~

Остановить окружение и удалить volume базы данных:

~~~bash
docker compose down -v
~~~

**Внимание:** `down -v` удаляет локальные данные PostgreSQL.

## HTTP API

Базовый путь: `/endpoints`.

### Управление эндпоинтами

| Метод | Путь | Описание | Успешный статус |
|---|---|---|---|
| POST | `/endpoints` | Создать эндпоинт | 201 |
| GET | `/endpoints` | Получить список эндпоинтов | 200 |
| GET | `/endpoints/{id}` | Получить эндпоинт по ID | 200 |
| PATCH | `/endpoints/{id}` | Обновить параметры эндпоинта | 200 |
| DELETE | `/endpoints/{id}` | Удалить эндпоинт | 204 |

Дополнительно:
- Фильтрация списка по `is_active`.
- Настройка интервала проверки при создании и обновлении.
- Изменение активности эндпоинта.
- URL нельзя изменить после создания.

### Проверки

| Метод | Путь | Описание | Успешный статус |
|---|---|---|---|
| POST | `/endpoints/{id}/checks` | Запустить проверку вручную | 200 |
| GET | `/endpoints/{id}/checks` | Получить историю проверок | 200 |

История проверок:
- Сортируется от новых результатов к старым.
- По умолчанию возвращается до 20 записей.
- Максимальный размер выборки — 100 записей.
- Размер выборки задаётся параметром `limit`.

Пример:

~~~http
GET /endpoints/1/checks?limit=5
~~~

Для несуществующего эндпоинта возвращается `404 Not Found`.

### Основные компоненты

- **Transport** — HTTP-обработчики, DTO, валидация входных данных и формирование JSON-ответов.
- **Repository** — взаимодействие с PostgreSQL через `pgxpool`.
- **Checker** — HTTP-проверки, обработка таймаутов и сетевых ошибок, измерение времени ответа и SSRF-защита.
- **Service** — координация проверки: получение эндпоинта, запуск Checker и сохранение результата.
- **Scheduler** — периодический запуск проверок активных эндпоинтов с ограничением параллелизма и блокировкой на уровне PostgreSQL.
- **Server** — регистрация HTTP-маршрутов.
- **Config** — загрузка конфигурации из переменных окружения.
- **Main** — инициализация зависимостей, запуск HTTP-сервера и Scheduler, graceful shutdown.

### Scheduler

- Интервал опроса Scheduler — 5 секунд.
- Максимальное количество одновременно выполняемых проверок — 5.
- Проверяются только активные эндпоинты, для которых наступило время проверки.
- Следующая проверка определяется на основе времени завершения предыдущей проверки и настроенного интервала.
- PostgreSQL advisory locks предотвращают одновременную проверку одного эндпоинта несколькими экземплярами приложения.
- Ошибка проверки одного эндпоинта не останавливает обработку остальных.
- При отмене контекста Scheduler прекращает работу.

## Безопасность проверок

Checker поддерживает HTTP и HTTPS. Таймаут проверки в текущей конфигурации приложения — 10 секунд. HTTP-редиректы автоматически не выполняются.

Для защиты от Server-Side Request Forgery (SSRF) используется Safe Dialer:

1. Проверяется URL и допустимость схемы.
2. Выполняется DNS-разрешение hostname.
3. Проверяются все полученные IP-адреса.
4. Соединение с непубличными IP-адресами запрещается.
5. Соединение устанавливается непосредственно с проверенным IP-адресом.

Это ограничивает возможность использовать сервис для обращения к локальным адресам и внутренним сетям.

## База данных

Используются две таблицы.

### `monitored_endpoints`

Хранит отслеживаемые эндпоинты:
- уникальный URL;
- интервал проверки в секундах;
- признак активности;
- время создания и последнего обновления.

### `check_results`

Хранит историю проверок:
- ссылка на эндпоинт;
- HTTP-статус;
- время ответа;
- время начала и завершения проверки;
- сообщение об ошибке;
- вычисляемый PostgreSQL признак успешности.

Поле `is_success` вычисляется на стороне PostgreSQL на основе HTTP-статуса `2xx`. При удалении эндпоинта связанные результаты удаляются каскадно.

Время ответа измеряется до получения HTTP-заголовков, а не до полной загрузки тела ответа.

## Тестирование

В проекте используются:

- **Transport tests** — проверка HTTP-обработчиков, валидации и JSON-ответов с помощью `httptest`.
- **Checker unit tests** — HTTP-ответы, сетевые ошибки, таймауты, отмена контекста и SSRF-защита.
- **Repository integration tests** — проверка взаимодействия с PostgreSQL.
- **Service unit tests** — проверка бизнес-логики с fake-зависимостями.
- **Scheduler unit tests** — периодические задачи, ограничение параллелизма, обработка ошибок, отмена контекста и освобождение блокировок.

Запуск unit-тестов:

~~~bash
go test ./...
~~~

Repository integration tests используют отдельную тестовую базу данных из `TEST_DATABASE_URL`. На ней должны быть применены миграции из каталога `migrations`. Не направляй эту переменную на базу с данными, которые нельзя изменять.

Дополнительные проверки:

~~~bash
go test -race ./...
go vet ./...
gofmt -l ./cmd ./internal
~~~

## CI

GitHub Actions запускает workflow при push в любую ветку, при Pull Request в `main` и вручную через GitHub Actions.

Pipeline:
1. Получает исходный код репозитория.
2. Устанавливает версию Go из `go.mod`.
3. Запускает PostgreSQL 18.6 как service container.
4. Устанавливает `golang-migrate` и применяет миграции к отдельной тестовой БД.
5. Запускает `go test ./... -v`.
6. Запускает тесты с race detector: `go test -race ./...`.
7. Выполняет `go vet ./...`.
8. Собирает Docker-образ приложения.

CI проверяет сборку и тесты, но не публикует Docker-образ и не выполняет deployment.
